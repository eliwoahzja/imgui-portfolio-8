# Токены и облачные конфиги

Это описание текущего протокола клиента и backend. Оно предназначено для
поддержки проекта, а не как публичное API. Не добавляй настоящий токен в код,
логи, скриншоты или переписки.

## Что хранится в облаке

Система использует два независимых вида конфигов:

| Назначение | Таблица MySQL | Ключ | Поведение |
| --- | --- | --- | --- |
| Личные конфиги на странице Config | `loader_user_configs` | `(game, uid, name)` | Можно сохранить, изменить, переименовать и удалить |
| Конфиги по Share-коду | `loader_cloud_configs` | `(game, base36 code)` | Неизменяемый снимок |

Для этого меню namespace игры равен `rf`. Конфиг из другого namespace не будет
виден этому меню, даже если владелец тот же.

## Откуда клиент берёт токен

Жизненный цикл production-токена выглядит так:

1. Авторизованный пользователь XenForo открывает `get-loader.php`.
2. Backend берёт последний неотозванный токен пользователя либо создаёт новый
   через `bin2hex(random_bytes(32))`. Результат - 64 hex-символа.
3. Пользователь перенаправляется в `dl.php?t=<token>`.
4. `dl.php` повторно проверяет токен и флаг `revoked`, обновляет `last_used_at`
   и `last_ip`, затем возвращает персонализированный exe с overlay.
5. При генерации токена из admin panel все прежние активные токены этого
   пользователя отзываются. Отозванный токен больше не проходит ни скачивание,
   ни cloud API.

Поскольку токен передаётся в query string скачивания, production access-логи
reverse proxy не должны сохранять полный параметр `t` в открытом виде.

Клиент ищет токен в следующем порядке и использует первый корректный вариант:

1. Overlay, добавленный в конец запущенного `.exe`.
2. Аргумент запуска `--token=<token>`.
3. Переменная окружения `RF_TOKEN`.
4. Файл `token.txt` рядом с `.exe`.

Обычный production-сценарий - overlay. Скрипт `dl.php` проверяет токен в
таблице `loader_tokens`, отклоняет отозванный токен, затем добавляет его в
конец шаблона загрузчика и отдаёт готовый exe.

Формат overlay: стартовый маркер, длина `uint16` little-endian,
XOR-обфусцированный ASCII-токен и конечный маркер. Это удобный способ доставить
токен вместе с exe, но не криптографическое хранилище. Сервер в любом случае
проверяет токен и его статус отзыва.

`token.txt` нужен только для локального тестирования. В файл рядом с exe нужно
положить только токен без кавычек и BOM. Клиент обрезает в конце пробелы и
переводы строк. Локально принимается printable ASCII длиной 10-128 символов,
но backend облака фактически принимает `[A-Za-z0-9]{16,64}` - используй именно
этот формат.

Не используй `--token` вне разработки: параметры командной строки доступны
другим процессам пользователя. `token.txt` не должен попадать в git или архив
релиза.

Исходники:

- чтение токена: `framework/net/token.cpp`;
- выдача персонального exe и создание overlay: backend `dl.php`;
- серверная проверка: backend `client/cloudcfg.php`.

## HTTPS и handshake

Клиент обращается по HTTPS к адресу, заданному в `framework/net/api.cpp`:
`https://rainfall.pw/forum/app.php`.

В исходниках backend gateway находится в `app.php`. Reverse proxy или web-root
должны сохранять публичный путь `/forum/app.php`, который зашит в клиент.
Gateway принимает только разрешённые зашифрованные операции и подключает
соответствующий обработчик из `client/`.

Перед каждой облачной операцией клиент создаёт новую сессию:

1. Генерирует случайный 48-символьный nonce из `[a-z0-9]`.
2. Отправляет зашифрованный `op=authentication` и две зашифрованные копии
   nonce: одну под bootstrap-ключами, вторую под ключом и IV, полученными из
   первых 32 и последних 16 символов nonce.
3. Сервер расшифровывает обе копии и требует точного совпадения.
4. Сервер создаёт session cipher длиной 32 символа, IV длиной 16 символов и,
   как правило, `sid` длиной 32 символа. Всё это возвращается под временными
   ключами nonce.
5. Клиент проверяет длины, расшифровывает ответ и добавляет `s=<sid>` в
   следующий запрос, если sid был возвращён.

Сессия хранится на backend и имеет скользящий TTL 30 минут. `sid` позволяет
пережить потерю PHP-cookie и исключает поиск сессии по общему Cloudflare IP.

После handshake запрос содержит зашифрованные сессионными ключами поля:

| Query-параметр | Расшифрованное значение |
| --- | --- |
| `op` | Имя операции, например `cloudcfg_list` |
| `a` | Токен загрузчика |
| `b` | Namespace игры, сейчас `rf` |
| `c` | Необязательные данные операции |
| `s` | Необязательный sid из handshake |

Backend расшифровывает `a`, ищет его в `loader_tokens`, проверяет отзыв,
получает пользователя XenForo и отклоняет забаненные или неактивные аккаунты.
UID и username клиента не являются источником авторизации и не передаются им
как доверенные поля.

Bootstrap-ключи и XOR-ключ намеренно не приведены в документации. Их смена без
одновременного выпуска совместимого клиента ломает протокол. Они также не
заменяют TLS - HTTPS остаётся обязательным.

## Формат конфига

`config_store::serialize()` собирает текст с фиксированным порядком полей:

```text
v=1
aim.enabled=1
aim.smoothing=0.2500
visuals.esp_enabled=1
settings.menu_opacity=0.9000
```

В документ попадают `aim`, `visuals` и нужные `settings`. Масштаб и DPI меню
не сохраняются, чтобы импорт чужого конфига не менял локальную геометрию окна.
При загрузке неизвестные поля игнорируются, а отсутствующие оставляют текущие
значения. Это сохраняет совместимость между версиями.

Перед отправкой имя и сериализованный текст кодируются в Base64. Backend
принимает имя `[A-Za-z0-9 _-]{1,48}`, printable ASCII-текст с переводами строк
и размер распакованного payload не более 64 KiB.

## Личная библиотека конфигов

Это операции страницы Config. Все они изолированы по `uid` и `game`:

| Операция | Содержимое `c` до шифрования | Ответ до шифрования |
| --- | --- | --- |
| `cloudcfg_list` | отсутствует | `ok;<count>;<name_b64>;<updated_ts>;...` |
| `cloudcfg_get` | `<name_b64>` | `ok;<name_b64>;<updated_ts>;<payload_b64>` |
| `cloudcfg_put` | `<name_b64>.<payload_b64>` | `ok;<updated_ts>` |
| `cloudcfg_delete` | `<name_b64>` | `ok` |
| `cloudcfg_rename` | `<old_name_b64>.<new_name_b64>` | `ok;<updated_ts>` |

`cloudcfg_put` работает как upsert: существующий конфиг обновляется, новый
создаётся. Лимит - 50 именованных конфигов на пользователя и игру. В БД поле
`payload` хранит Base64-текст, а не уже декодированный документ.

При старте меню в фоне запрашивает список и загружает первый конфиг. Если
личная библиотека пуста, оно проверяет старые файлы
`<папка exe>\configs\*.cfg` и загружает подходящие в облако. Старые файлы не
удаляются, но больше не являются главным хранилищем. Если мигрировать нечего,
создаётся облачный конфиг `Default`.

Save, Load, Create, Duplicate, Delete, Rename, Share и Import выполняются
вне UI-потока. Autosave ждёт 1.5 секунды после последнего изменения и отправляет
данные через свой фоновый writer.

## Share-коды

Share-код - неизменяемый снимок, а не ссылка на личный конфиг. Поэтому уже
переданный конфиг не изменится, если его автор позже отредактирует или удалит
свою личную версию.

| Операция | Содержимое `c` до шифрования | Ответ до шифрования |
| --- | --- | --- |
| `cloudcfg_save` | `<name_b64>.<payload_b64>` | `ok;<base36_code>` |
| `cloudcfg_load` | `<base36_code>` | `ok;<code>;<uid>;<name_b64>;<username_b64>;<payload_b64>` |

`cloudcfg_save` создаёт новый случайный 20-символьный код `[a-z0-9]` и новую
строку в БД. Лимит - 50 снимков на пользователя и игру; старые снимки не
удаляются автоматически. При импорте клиент читает снимок, выбирает свободное
имя и сохраняет его в личной библиотеке импортирующего пользователя.

## Подготовка backend

Параметры БД задаются в backend `client/settings.php`:

- `CFG_DB_HOST`, `CFG_DB_USER`, `CFG_DB_PASS`, `CFG_DB_NAME` могут указывать
  на отдельную БД;
- без этих переменных используются host, пользователь и схема XenForo;
- `CFG_DB_TABLE` по умолчанию равен `loader_cloud_configs`.

После деплоя выполни миграцию в PHP-контейнере:

```powershell
docker exec -i xenforo-php php /var/www/html/client/migrate_cloudcfg.php
```

Пользователю БД достаточно права создавать и менять таблицы в настроенной
схеме. Глобальное право `CREATE DATABASE` не требуется. Миграция создаёт
`loader_cloud_configs` и `loader_user_configs`.

`cloudcfg.php` блокирует IP, накопивший 30 неудачных попыток входа за пять
минут, ещё до выполнения новой cloud-операции. Для управляемых полей SQL
используются prepared statements.

## Диагностика

| Симптом | Причина | Что проверить |
| --- | --- | --- |
| `Token not found` | Не найден корректный overlay, аргумент, env или `token.txt` | Для теста положить `token.txt` рядом с exe, без BOM и кавычек |
| `invalid_credentials` | Токен не существует или отозван | `loader_tokens` и токен в скачанном exe |
| `banned` | Пользователь забанен или не имеет XenForo state `valid` | Поля пользователя в `xf_user` |
| `data_error` | Не прошла миграция или ошибка подключения к БД | Выполнить миграцию, проверить `CFG_DB_*` и права на таблицы |
| `limit_reached` | Достигнут лимит 50 личных конфигов или 50 snapshot-кодов | Удалить лишние личные конфиги; snapshot-коды удаляются только осознанной очисткой БД |
| Индикатор офлайна | HTTPS не получил HTTP 200 с телом | Путь gateway, reverse proxy, DNS, сертификат, логи PHP и контейнера |

Клиент проверяет доступность gateway в фоне каждые 10 секунд. При непрерывном
офлайне интерфейс не блокируется, показывает индикатор и завершает процесс
через пять минут. HTTP 200 с непустым телом сбрасывает таймер.
